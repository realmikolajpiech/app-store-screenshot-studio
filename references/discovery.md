# Evidence before copy

## Find the real product

Start from screens and trace actions users can complete. Inspect backing
features, contracts and flags as needed. Onboarding reveals intended framing;
paywalls reveal availability boundaries. A type, mock response or TODO alone
does not prove a shipped feature. Existing metadata and authorized reviews
provide the customer's vocabulary. Without code, use captures and the user's
description, marking uncertain claims instead of blocking useful planning.

Record project-relative evidence or source links. Do not copy code or customer
records into public examples. A compact table is enough:

| Audience | Friction | Outcome | Implementation evidence | Visual proof | Confidence |
| --- | --- | --- | --- | --- | --- |
| Busy home cook | Ingredients go unused | Plan dinners around food at home | Ingredient matching and plan flow | Populated weekly plan | Implemented; demand unverified |

Ask only what the evidence cannot answer: which audience leads, whether a flag
ships, language, or display slot. Group meaningful questions. Do not ask the user
to explain the whole app after reading it. Continue independent preparation.

## Rank and sequence

Prefer promises relevant to this audience, distinct from adjacent promises, and
supported by unmistakable visual proof. This is editorial judgment, not a made-up
conversion score. One possible arc is core outcome -> mechanism -> another
benefit -> confidence/progress/breadth. It is not a fixed template. The first few
images should explain the product without relying on later panels.

Keep secondary audiences from confusing the first promise. An instructor frame
can close a student-led story; a team product might warrant a separate campaign.
Make a necessary audience shift explicit rather than mixing identities.

## Copy laboratory

Try different angles for the first promise, then select the strongest:

| Angle | Candidate | Required evidence |
| --- | --- | --- |
| Outcome | A dinner plan that fits your week | Editable weekly plan |
| Mechanism | Turn your ingredients into dinner | Ingredient-based suggestions |
| Relief | Less deciding. More cooking. | Demonstrable planning flow; no quantified savings |

Use natural local phrasing. In Polish, preserve diacritics, inflection and readable
line breaks; do not separate a short preposition from its phrase to imitate an
English poster. Emphasize the useful noun or outcome; the verb need not be the
largest word. Do not enforce one font, language, palette or line count globally.

Reject generic aspiration, feature inventories, developer vocabulary, and
unsupported “best,” “instant,” “guaranteed,” or numerical claims. Visual polish
does not establish conversion uplift; that requires a controlled outcome test.

## Pair and capture

Inspect pixels. A chart can prove tracking, not necessarily better performance.
A confirmation button can prove scheduling, not instant availability. An
intentional empty state, settings screen or login flow can be valid if it is
exactly the selling point, rather than a substitute for missing product content.

Retake instructions specify route, state, data, appearance and focal content.
Use the project's authorized showcase environment. Do not mutate live customer
data for a capture. Normalize distracting chrome where supported; preserve real
theme and selected state. Record anonymization substitutions before generation
so phone UI and enlarged cards do not drift into different identities.

## Recover capture failures before handing work back

Inspect the project's run instructions, actual available tools, existing running
app/dev server and permitted capture routes. If the user excluded old screenshots,
do not inspect or reuse those files; capture the current application instead.

When a launch or capture fails, identify the concrete failure from the command
output or UI state. Apply a targeted, reversible correction within the authorized
scope, then retry. For example, distinguish an exited server, wrong URL or port,
browser connection problem, missing runtime, and an authentication requirement.
A successful web build is not a running preview; start or serve it using the
project's supported commands, verify it responds, then capture through available
browser tools. Do not repeat an unchanged failing command without new evidence.

If that route is genuinely unavailable, try another existing supported route:
an accessible native app/simulator, a development preview, or the project's web
target if it faithfully renders the relevant interface. Record source platform
and visible differences; do not label web captures as native. Respect explicit
device/emulator prohibitions. Do not install large SDKs, invent a replacement UI
or change application behavior just to manufacture proof.

Ask the user only for the remaining external dependency once available permitted
routes have been exhausted or a concrete access boundary is established. State
briefly what failed and why the fallback cannot proceed, then request the smallest
useful intervention (such as starting the native app or supplying two specified
screens). Continue independent copy and art-direction work, but label the state
accurately: “brief ready; captures and artwork pending,” never “finished graphics”
when no graphics exist. With captures and generation available, continue through
production instead of stopping at the plan unless the user requested a pause.
